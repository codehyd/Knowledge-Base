# 空库笔记编辑器：双模统一与 SDK 化实施计划

> 状态：草案（待评审）
> 创建日期：2026-08-06
> 关联范围：`apps/web` 笔记编辑器、`apps/api` vault 模块

---

## 1. 背景与目标

### 1.1 现状痛点

当前笔记区实现了"Markdown 模式 + 语雀（Lake）模式"双编辑器，但存在以下问题：

| 问题 | 现状 | 影响 |
| --- | --- | --- |
| 一篇笔记两个文件 | `.md` 与 `.lake` 同目录双份存储（vault 模块中为"实验"标记） | 改一处需同步两处，diff/冲突/迁移都困难 |
| 双引擎双文档树 | TipTap（MD 编辑器）与 `yuque-editor-core`（Lake 编辑器）各自维护文档状态 | 互转依赖 turndown，往返易丢格式、产生抖动 |
| 语雀引擎副作用 | Lake 会注入 antd v4 全局样式，当前靠 MutationObserver 兜底禁用 | 样式污染风险高，独立打包时是负债 |
| 扩展能力受限 | 扩展注册表仅支持声明式 slash 项与双链，不能注册自定义块 | 无法支撑"高可扩展性"卖点 |
| 与业务耦合 | 两个编辑器都直接依赖 API client、笔记树、双链解析 | 无法作为独立 SDK 复用 |

### 1.2 目标

1. **单文件**：一篇笔记只保留一个 `.md` 文件，块编辑只是该文件的另一种视图。
2. **保留语雀级体验**：斜杠命令、提示块、数据库、看板等高级块全部可编辑，存储为 Markdown 方言。
3. **MD 兼容**：文件始终是合法 Markdown，外部工具可读、数据不锁定。
4. **可扩展可自定义**：提供四层插件 API（内容、格式、交互、外观），面向未来的可嵌入 SDK（B 路线）。
5. **干净边界**：编辑器内核与空库业务（API、vault、知识库）彻底解耦，可独立成包。

### 1.3 非目标（本期不做）

- 移动端适配
- 多人协同编辑
- SaaS 托管
- 完整独立 SDK 的商业化发布（仅做边界固化与验证）

## 2. 现状盘点（代码事实）

| 组件 | 技术栈 | 职责 | 关键问题 |
| --- | --- | --- | --- |
| `MarkdownEditor` | TipTap 3.29 + tiptap-markdown | MD 所见即所得、斜杠菜单、双链 | 文档树与 Lake 不一致 |
| `LakeEditor` | `yuque-editor-core@0.0.7` + turndown | 语雀式富文本编辑 | 依赖 0.x、样式污染、双份存储 |
| `editor-extensions` | 声明式 manifest | slash 项与双链 mark 注册 | 无自定义块能力 |
| `vault` 模块 | SQLite + 文件系统 | 多级文件夹、保存自动入库 | `.lake` 双份存储 |
| `wikilink` | 自定义解析/扩展 | 双链补全、跳转 | 与编辑器耦合 |

已具备的有利条件：

- 双编辑器均已可用，切换逻辑（`lakeMode`）已实现；
- 已有扩展注册表雏形（`EditorExtensionManifest`、`DeclarativeSlashItem`）；
- 已有 turndown + GFM 的 MD 转换基础；
- 笔记保存后自动入库（chunking + embedding）链路完整。

## 3. 目标架构

### 3.1 单源真相模型

```
                ┌─────────────────────────────┐
                │        唯一的 .md 文件        │  ← 存储层（唯一真相）
                └──────────────┬──────────────┘
                               │ 解析 / 序列化
                ┌──────────────▼──────────────┐
                │       文档模型（AST）          │  ← 模型层（统一结构）
                └──────────────┬──────────────┘
              ┌────────────────┼────────────────┐
     ┌────────▼────────┐  ┌───▼───────────┐
     │ MD 视图（TipTap） │  │ 块视图（Lake） │  ← 视图层（两种皮肤）
     └─────────────────┘  └───────────────┘
```

核心原则：

- 文档只有一份真相（`.md`）；
- MD 视图与块视图都是文档模型的"渲染器"；
- 两个视图的修改都通过**规范序列化器**写回 `.md`；
- 高级块在编辑时为可交互组件，落盘时为方言语法，读取时还原。

### 3.2 兼容分层

| 层级 | 内容 | 兼容性 |
| --- | --- | --- |
| T1 基础层 | 标题、列表、表格、代码块、任务清单、引用 | 标准 MD，任何工具可读可编辑 |
| T2 方言层 | 提示块、数据库、看板等高级块 | 本文档内渲染为组件；外部工具显示为代码块源码，不损坏 |
| T3 保真层 | 复杂嵌套/交互式块 | 仅本文档完整保真 |

## 4. 核心设计决策

### D1：规范序列化器替代 turndown

- 为每个块类型定义三件套：**组件 ↔ 方言 ↔ 渲染**；
- 序列化规则固定（有序列表写法、表格对齐、空行规则），保证往返不抖动；
- 建立往返测试矩阵：`MD → AST → 块视图 → MD` 与 `MD → AST → MD` 必须幂等。

### D2：方言语法编码高级块

- 使用围栏代码块 + 前缀标记，例如：

````markdown
## 项目清单

```kongku:db
| 名称   | 状态   | 优先级 |
| ------ | ------ | ------ |
| 调研   | 进行中 | 高     |
```
````

- 前缀命名空间统一为 `kongku:`，避免与其他工具冲突；
- 方言内容对标准 Markdown 解析器天然降级为代码块。

### D3：元数据使用 YAML frontmatter

- 笔记标题、创建时间、标签、关联源等元数据放文件头 `---` 块；
- 正文保持纯 Markdown。

### D4：四层插件 API

| 层 | 能力 | 示例 |
| --- | --- | --- |
| 内容扩展 | 自定义块、自定义 mark、斜杠命令 | 提示块、看板、思维导图 |
| 格式扩展 | 自定义序列化/导入导出 | 对接客户私有格式 |
| 交互扩展 | 工具栏、气泡菜单、快捷键、联想 | 双链联想、表格操作条 |
| 外观扩展 | 主题、白标 | 嵌入方品牌化 |

插件 API 设计原则：

- 从"声明式"升级为"受控插件"（可注册自定义块与序列化器）；
- 安全边界：第三方插件默认沙箱/声明式，信任插件可执行代码；
- 类型化 manifest，版本兼容策略。

### D5：迁移策略

- 一次性迁移脚本：读取 `.lake` → turndown 转换 → 合并进 `.md` → 删除 `.lake`；
- 迁移前备份 `data/vault`；
- 迁移后全量验证：笔记数量、内容一致性、双链完整性。

### D6：资产与文档分离

- 图片、附件等资产放 `attachments/`，文档内相对路径引用；
- "一份文件"指文档文件，资产独立存放不影响该原则。

## 5. 分阶段实施计划

### Phase 0：方案定稿（约 1 周）

**目标**：验证关键风险，冻结设计。

- [ ] 用最小 demo 验证"统一文档模型 + 双视图"可行
- [ ] 敲定方言语法规范与命名空间
- [ ] 评估 Lake 引擎长期保留还是中期替换（决策 B1/B2）
- [ ] 输出《文档模型规范》与《方言规范》

**验收**：本文档所有 D1-D6 有明确实现方案。

### Phase 1：单文件化（约 2-3 周）

**目标**：消灭 `.lake` 双份存储。

- [ ] 实现规范序列化器（替代 turndown）
- [ ] 实现 YAML frontmatter 元数据读写
- [ ] 编写迁移脚本并演练（备份 → 迁移 → 验证）
- [ ] 删除 `.lake` 存储逻辑，清理相关代码
- [ ] 建立往返测试矩阵

**验收**：所有笔记仅一个 `.md`；模式切换 100 次往返内容不变。

### Phase 2：方言与高级块（约 3-4 周）

**目标**：语雀级体验落地到 MD 文件上。

- [ ] 实现方言解析器与序列化器
- [ ] 第一批高级块：提示块、数据库、看板、任务清单增强
- [ ] 高级块组件化（可拖拽、可配置）
- [ ] 外部工具打开时的降级表现测试

**验收**：高级块在本文档内完整保真，外部工具中降级为合法代码块。

### Phase 3：解耦与插件 API（约 3-4 周）

**目标**：编辑器内核可独立复用。

- [ ] 抽象编辑器依赖接口（内容提供、保存、链接解析、文件树）
- [ ] 解耦 API client 与 vault 业务
- [ ] 插件 API 升级：自定义块注册、序列化器注册、工具栏/主题注入
- [ ] 编写插件 API 文档与示例插件

**验收**：编辑器可在空库之外的最小 demo 中运行并加载示例插件。

### Phase 4：SDK 化验证（持续）

**目标**：为 B 路线（可嵌入编辑器引擎）铺路。

- [ ] 将编辑器内核拆为独立包（含类型与插件 API）
- [ ] 输出嵌入文档：React/Vue 接入示例、主题白标示例
- [ ] 找 1-3 个潜在 B 端用户验证付费意愿
- [ ] 视反馈决定：开源核心 + 企业授权 / 托管服务

## 7. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| Lake 引擎 0.x、维护风险 | 升级断裂、样式污染 | 适配层隔离；中期规划统一内核 |
| 双引擎状态不同步 | 往返丢格式、抖动 | 统一 AST + 规范序列化器 + 幂等测试 |
| 方言兼容性 | 外部工具表现降级 | 明确 T1/T2/T3 分层，降级为合法代码块 |
| 工作量失控 | 项目停滞 | 分阶段交付，每阶段独立可用 |
| 迁移丢数据 | 用户笔记损坏 | 备份、演练、校验脚本 |

---

## 8. 总体验收标准

1. 一篇笔记且仅有一个 `.md` 文件；
2. MD 模式与块模式切换往返无损、文件内容稳定；
3. 高级块（提示块、数据库、看板）编辑体验达到语雀级；
4. 文件用任意标准 Markdown 工具打开仍为合法文档；
5. 插件 API 支持四层扩展，编辑器可在空库外独立运行；
6. 无 `.lake` 残留、无 API client 直接依赖。
