# 功能点 10：公版书（从零到一）

> 本篇回答：**怎样把 Gutenberg、维基文库等四个互不相同的公版书源，包装成统一的"搜索 → 一键喂养"体验？**

---

## 1. 这个功能解决什么问题？

空库默认是空的，冷启动时用户没资料可喂。公版书（版权过期的经典书籍）是最好的初始口粮。但：

1. 各书源的 API 千差万别（Gutendex 是 JSON REST、维基文库是 MediaWiki API、ctext 要 Key、中文镜像只是个 CDN 目录）；
2. 书源在国外，**网络不可达是常态**，不能一个源挂了就全挂；
3. 下载一本书可能几十秒，需要异步任务 + 进度反馈。

## 2. 先修概念

- **Protocol（结构化鸭子类型）**：Python 的接口约定方式——不需要继承基类，只要实现了约定的方法就算实现了接口。
- **组合模式**：一个"外层对象"内部持有几个"内层对象"，对外表现为一个整体。
- **Content-Disposition**：HTTP 响应头，告诉浏览器"这是附件，下载它，文件名叫 xx"。

## 3. 从零推导

### 第一步：统一接口——两个方法屏蔽一切差异

```python
# apps/api/app/modules/open_books/providers/base.py:10-18
class BookProvider(Protocol):
    info: OpenBookSourceInfo

    async def search(self, query: str, *, page: int = 1) -> tuple[list[OpenBookItem], int]:
        ...

    async def fetch(self, book_id: str) -> tuple[bytes, str, str]:
        """返回 (文件内容, 文件名, 标题)。"""
        ...
```

注册表（`providers/__init__.py:9-38`）：

```python
_PROVIDERS = {
    "zh_open": ZhOpenProvider(),
    "ctext": CtextProvider(),
    "wikisource_zh": WikisourceZhProvider(),
    "gutenberg": GutenbergProvider(),
}
_ALIASES = {"chinese_classics": "zh_open", "cdn_mirror": "zh_open"}  # 兼容旧 id
```

**设计解读**：核心契约只有两个方法——`search` 返回统一结构的条目列表，`fetch` 返回 `(bytes, filename, title)` 三元组。上游 service 完全不关心背后是哪种 API。**用 Protocol 而非 ABC 继承**，各 provider 互不依赖、可独立增删。`_ALIASES` 别名表是兼容层：书源改名后，旧前端/旧配置传入的 id 仍能路由。

### 第二步：组合 provider——一个书源、三条链路

中文公版书源 `zh_open` 内部其实是个"套娃"（`providers/zh_open.py:142-162` 节选）：

```python
# 3) 镜像/本地均未命中 → 维基文库外搜（失败则友好空结果，不整页报错）
if not hits:
    try:
        wiki_items, wiki_total = await self._wiki.search(q, page=page)
    except HTTPException:
        raise HTTPException(status_code=404, detail="镜像与本地未找到匹配，且维基文库暂时不可达。可换关键词，或稍后再试 / 本地上传。")
    for it in wiki_items:
        it.source = "zh_open"
        it.id = f"wiki:{it.id}"       # 加前缀，fetch 时按前缀路由回真实现
```

**设计解读**：`zh_open` 内部持有 `WikisourceZhProvider` 实例，搜索按 **本地内置文本（道德经/千字文/三字经）→ GitHub 镜像目录（jsDelivr CDN）→ 维基文库** 三级降级。外搜结果改写 id 加 `wiki:` 前缀、source 伪造成 `zh_open`——**用户面对一个书源，享受三条链路的可用性**；fetch 时按 id 前缀（`local:` / `mirror:` / `wiki:`）分发回真正的实现。本地内置文本保证了"完全断网也有书可读"。

### 第三步：异步导入——进程内任务注册表

```python
# apps/api/app/modules/open_books/jobs.py:13-41（节选）
@dataclass
class ImportJob:
    id: str
    status: JobStatus = "pending"
    progress: int = 0
    message: str = "排队中…"
    ...

_JOBS: dict[str, ImportJob] = {}

def create_job(...) -> ImportJob:
    job = ImportJob(id=uuid.uuid4().hex[:16], ...)
    _JOBS[job.id] = job
    # 简单清理：超过 200 个任务时丢掉最旧的已结束任务
    if len(_JOBS) > 200:
        ...
```

**为什么用内存 dict 而不是 Redis？** 文件头注释直言"进程内，个人版够用"。配一个"超 200 丢最旧 50 个已完成"的简易 GC 防内存膨胀。路由层 `POST /import` 用 BackgroundTasks 触发，立即返回 job_id，前端轮询 `GET /jobs/{job_id}`。

进度是**阶梯式手动打点**（8 → 20 正在下载 → 70 写入队列 → 90 → 100）而非真实字节进度——"假进度条"的典型实现：进度点按代码阶段设置，对用户来说"在动 + 有中文文案"就够了。

### 第四步：「另存为」——为什么直接返回文件流

```python
# apps/api/app/modules/open_books/router.py:81-118（节选）
@router.get("/file", summary="另存为：拉取电子书文件到本机", description="直接返回文件流，不进入喂养队列。")
async def download_open_book_file(...):
    data, filename, title = await open_books_service.fetch_file(...)
    safe_name = _attachment_name(title=display_title, original_filename=filename)
    ascii_name = safe_name.encode("ascii", "ignore").decode("ascii") or "book_....txt"
    encoded = quote(safe_name)
    return Response(
        content=data,
        headers={
            "Content-Disposition": f"attachment; filename=\"{ascii_name}\"; filename*=UTF-8''{encoded}",
            "X-Kongku-Filename": encoded,
        },
    )
```

**设计解读**：
- "另存为"与"喂养入库"是两条互斥路径——此接口绕过 sources 队列，后端只当中转代理（provider 拉到 bytes 原样回吐）。
- **中文文件名的标准处理**：`Content-Disposition` 双写——ASCII 兜底的 `filename=`（老浏览器）+ RFC 5987 的 `filename*=UTF-8''<urlencoded>`（新浏览器）；再额外发 `X-Kongku-Filename` 自定义头供前端 fetch 场景读取（这就是功能点 01 里 CORS `expose_headers` 存在的原因）。
- **用 GET 而非 POST**：浏览器可以直接当下载链接打开。

## 4. 完整流程图

```
搜索：GET /api/open-books/search?query=道德经
   │ get_provider(source) 路由到对应 provider
   │ zh_open：本地 texts/ → jsDelivr 镜像目录 → 维基文库（三级降级）
   ▼
统一 OpenBookItem 列表（id 带 local:/mirror:/wiki: 前缀）
   │
   ├─ 喂养：POST /import → create_job → 后台 fetch → 写入 sources 队列
   │     （走功能点 03~06 标准流水线；provenance=open_book, book_kind=confirmed → 上书架）
   │     前端轮询 GET /jobs/{job_id}（8→20→70→90→100）
   │
   └─ 另存为：GET /file → fetch → Response 文件流（双写文件名头）
```
