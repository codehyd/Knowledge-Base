# 功能点 08：RAG 知识对话与拒答（从零到一）

> 本篇回答：**项目最核心的功能——怎样让 AI "只按你喂过的资料"回答，没资料就老实拒答，还能标出可信度和出处？**

---

## 1. 这个功能解决什么问题？

直接问 ChatGPT/DeepSeek，它会凭"常识"回答——但常识会过时、会记错、会一本正经地胡说（幻觉）。空库要做的是：

1. **检索先行**：回答问题前，先在你的知识库里找相关段落，回答只能基于这些段落；
2. **诚实拒答**：库里没有足够证据时，明确说"资料不足"，绝不编造；
3. **可信度透明**：每个回答标注 ok（可信）/ suspect（存疑）/ conflict（资料冲突）；
4. **引用可溯**：每个知识点都能跳回原文高亮。

还有工程问题：一次问答 = embedding + 全库检索 + LLM 生成 + 引用对齐，可能 10~30 秒——**HTTP 同步等待会超时**。

## 2. 先修概念

- **RAG（检索增强生成）**：Retrieval-Augmented Generation。先从知识库检索相关内容，再把"问题 + 检索结果"一起给 LLM 生成回答。
- **余弦相似度**：度量两个向量方向的接近程度（-1~1），越接近 1 语义越相近。
- **异步任务 + 轮询**：请求受理后立即返回"受理号"，实际计算在后台跑，客户端定时查询结果。

## 3. 从零推导

### 第一步：为什么"受理即返回"而不是同步等待

```python
# apps/api/app/modules/chat/router.py:61-78（节选）
async def chat(payload: ChatIn, background_tasks: BackgroundTasks, db = Depends(get_db)):
    out = await chat_service.begin_chat(db, payload)
    if out.status == "pending" and out.pending_message_id is not None:
        background_tasks.add_task(run_chat_job, out.pending_message_id)
    return out
```

受理时在**同一事务**里落两条消息（`chat/service.py:947-974`）：用户消息（status=done，立即可见）+ 助手占位消息（status=pending, progress=accepted）。前端轮询 `GET /chat/sessions/{id}/messages` 直到 `status != "pending"`。

**为什么这样设计**：
- 同步等待 30 秒会撞网关超时、前端断连、用户切页丢答案。受理即返回后，响应时间恒定毫秒级，**用户切走页面再回来，答案也丢不了**（消息已落库）。
- `progress` 字段（accepted → retrieving → generating → citing）让前端能显示"正在检索/正在生成/正在核对出处"的阶段动画——把黑盒等待变成可感知进度。
- 后台任务用 FastAPI `BackgroundTasks` 而非 Celery：单机工具不引入消息队列（与功能点 03 同一哲学）。任务内**新建 Session、只传消息 id**（`chat/tasks.py`），注释点明原因："避免切库热切换后仍用旧引擎"。

### 第二步：检索——两级漏斗

```python
# apps/api/app/modules/chat/service.py:1282-1331（节选）
async def _retrieve(self, db, message, *, category_id):
    q = select(Chunk, Entry).join(Entry, ...)
    if category_id is not None:
        q = q.join(EntryCategory, ...).where(EntryCategory.category_id == category_id)
    rows = list((await db.execute(q)).all())

    # 尝试向量
    query_vecs = await embed_texts(db, [message])
    if query_vecs and query_vecs[0]:
        scored = []
        for chunk, entry in rows:
            vec = load_embedding(chunk.embedding)
            if not vec:
                continue
            sim = cosine_similarity(qv, vec)
            if sim >= VECTOR_MIN_SCORE:      # 0.28
                scored.append((chunk, entry, sim))
        if scored:
            return sorted(scored, ...)[:TOP_K], "vector"   # TOP_K=6

    # 关键词降级
    for chunk, entry in rows:
        if _is_noisy_chunk(chunk.text):
            continue                        # 滤掉版权页/ISBN 这类"命中词多但无知识"的切片
        score = _keyword_score(chunk.text, tokens)
        score += _keyword_score(entry.title, tokens) * 1.2   # 标题命中加权
        if score >= KEYWORD_MIN_SCORE:      # 1.5
            ...
    return scored_kw[:TOP_K], "keyword"
```

**设计决策逐条解读**：
- **为什么全量加载切片而不是数据库内检索？** 向量存的是 JSON 文本（功能点 07 的零依赖取舍），只能读回内存算。个人知识库千级切片，暴力扫描毫秒级完成。
- **阈值 0.28 偏宽松**：个人语料小，宁多勿漏——漏了的代价是拒答，多给的代价只是 prompt 略长。
- **降级路径**：embedding 不可用（无 Key/失败）时自动走关键词打分，两条路径**共用 TOP_K=6 的输出契约**，上层无需分支。
- **标题加权 ×1.2**：用户提问里的概念词若出现在书名/标题中，该条目所有切片都应加分。
- **`category_id` 在 SQL 层限定**："只在某个分类里问"是检索范围约束而非后置过滤——保证 TopK 不被范围外切片挤占。

### 第三步：拒答——两道闸门 + 第二意见

```python
# chat/service.py:96-134（节选）
def _looks_like_refusal(answer: str) -> bool:
    head = (answer or "").strip()[:100]
    if head.startswith("资料不足"): return True
    if "无法有依据地回答" in head: return True
    ...

def _hits_seem_relevant(message, chunk_texts, scores, *, mode) -> bool:
    """检索已命中时，粗判是否值得强制作答（防止模型误拒）。"""
    if len(tokens) <= 3: return True        # 问句很短：有命中就倾向作答
    for text in chunk_texts:
        if _keyword_score(text, tokens) >= 1.0: return True
    top = max(scores)
    if mode == "vector" and top >= VECTOR_MIN_SCORE: return True
    ...
```

**拒答的完整机制**：
1. **第一道闸门（检索层）**：检索零命中 → 直接拒答，不调 LLM（省钱省时）；
2. **第二道闸门（生成层）**：LLM 在 system prompt 约束下自行判断，输出拒答话术；
3. **第二意见（仲裁层）**：`_looks_like_refusal` 只检查回答开头 100 字（拒答措辞是 prompt 里约定好的）。如果模型说"资料不足"，但检索分数明明达标（或问句很短、或切片关键词命中），判定为**误拒**——不信任模型的自我判断，用可计算的检索信号做仲裁。

误拒后的强制重答（`service.py:1188-1206`）：system prompt 尾部追加 `_RETRY_AFTER_FALSE_REFUSAL`（"禁止回复「资料不足」"），temperature 压到 0.1 降随机性，再生成一次。**重试后仍像拒答才真正 `refused=True`**——拒答结论经过双重确认。

### 第四步：可信度——为什么用"标记尾巴"而不是 JSON

```python
# chat/service.py:64-68
# 模型须在正文末尾单独一行输出该标记，便于解析；不会展示给用户。
TRUST_MARKER_RE = re.compile(r"<<<TRUST:(ok|suspect|conflict)(?:\|([^\n>]*))?>>>", re.IGNORECASE)
```

**设计解读**：需要 LLM 同时产出"给人看的正文"和"给程序看的元数据"时，**定界符标记比 JSON 结构化输出更稳**——模型不擅长在长正文后保持合法 JSON（多一个逗号就解析失败）。要求它在末尾单独一行输出 `<<<TRUST:suspect|资料发布时间较早>>>`，解析时剥离。

解析细节（`_parse_trust_trailer`，`service.py:137-175`）：遍历所有匹配取**最后一个**（防止正文里意外出现类似字样误伤）；找不到标记还有关键词弱兜底（正文提到"资料本身有误/彼此冲突"则推断 trust）——**trust 永远能落到三值之一，程序永不为难**。

### 第五步：引用对齐——从答案反推原文

朴素做法是把"切片开头"当引用位置，但那常常落在残句上。本项目的做法反过来（`_align_citations_with_answer`）：

1. 从**回答文本**里提取知识点（加粗词、编号项、「引号词」）；
2. 拿知识点回原文定位（切片内偏移 `local_idx` + 切片基址 `chunk_base` = 全文偏移，**多级文本坐标必须显式换算基址**）；
3. `expand_to_complete_passage` 扩成有头有尾的完整段落（30~320 字）。

之后还有 AI 精修（`_ai_refine_quotes`）：把每个知识点的上下文窗口交给 LLM，要求逐字摘出 40~300 字完整 quote。三个细节：
- `quote_refine_max_tokens` 默认 8000，因为**推理模型会把 token 耗在思考过程上**，余量不足正文会被截空；
- 失败返回 None——精修是锦上添花，绝不拖垮主流程；
- AI 给的 quote 还要重新定位回原文偏移（`_punct_fuzzy_spans` 忽略标点模糊匹配）——**不信任 AI 给的坐标，只信任它给的文本**。

主流程先 `ai_refine=False` 快速出答案，再后台精修更新引用——"先快后好"两阶段提交。

### 第六步：沉淀闭环——引用落成预笔记

每条对齐后的引用调 `ensure_chat_anchor` 落成（或合并进）`kind="chat_anchor"` 预笔记（功能点 07），返回的 citation 带 `annotation_id`——前端点引用即跳到阅读页对应高亮。单条落库失败只 pass 不影响其他引用。**对话反向滋养知识库，在此闭环。**

## 4. 完整流程图

```
POST /api/chat
   │ 同事务落库：用户消息(done) + 助手占位(pending/accepted)
   │ 立即返回 pending_message_id
   ▼
后台 run_chat_job
   │ progress=retrieving
   ├─ _retrieve：向量余弦(≥0.28) → TopK6；失败降级关键词(标题×1.2)
   │    └─ 零命中 → 拒答落库（不调 LLM）
   │ progress=generating
   ├─ LLM 生成（技能包 preamble 注入，见功能点 11）
   ├─ _parse_trust_trailer 剥离 <<<TRUST:...>>>
   ├─ 像拒答 且 检索达标？→ 强制重答一次（temperature=0.1）
   │ progress=citing
   ├─ 引用对齐（本地启发式）→ 落 chat_anchor 预笔记
   └─ 后台 AI 精修摘段 → 更新 citations_json
   ▼
status=done：answer + refused + trust + trust_note + citations[] + retrieval(vector|keyword)
```
