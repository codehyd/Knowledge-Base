# 功能点 03：喂养投递（从零到一）

> 本篇回答：**用户丢进来一个文件 / 一段笔记 / 一个链接，系统怎么接住它、放进队列、异步解析，还能让用户随时看到进度？**

---

## 1. 这个功能解决什么问题？

"喂养"是空库的入口动作。朴素的想法是：用户上传 → 后端解析 → 返回结果。但真实场景里解析可能要几分钟（OCR 一本扫描书、转写 20 分钟视频），HTTP 请求不可能一直挂着。于是需要解决：

1. **投递要秒回**，解析在后台慢慢跑；
2. **解析会失败**，失败后用户要能重试、能补材料；
3. **三种投递方式**（上传文件 / 粘贴笔记 / 贴链接）要统一处理，下游不该关心来源差异；
4. **进度要可见**，用户盯着队列页面时能看到"走到哪一步了"。

## 2. 先修概念

- **状态机（State Machine）**：一个对象在固定几种状态间流转（pending → processing → ready → committed），每个状态只允许特定操作。它是异步流水线的"交通灯"。
- **BackgroundTasks**：FastAPI 自带的后台任务机制——响应返回后，在同一进程里继续执行函数。不需要 Celery/Redis 这种重型队列。
- **轮询（Polling）**：前端定时问后端"好了吗"，直到状态变化。比 WebSocket 简单，个人工具够用。

## 3. 从零推导

### 第一步：一张表接住所有投递——sources 表与状态机

```python
# apps/api/app/modules/sources/models.py:7-35
class Source(Base):
    """喂养来源：电子书 / 笔记 / 链接。解析确认前都挂在此表。"""

    id = mapped_column(Integer, primary_key=True, autoincrement=True)
    # ebook | note | url | video_url | video_file
    type = mapped_column(String(50), index=True, default="note")
    # 投递出处：open_book（公版书库）| upload（本地上传）
    provenance = mapped_column(String(40), default="", index=True)
    # 书籍可信度：confirmed（上书架）| possible（可能为书）
    book_kind = mapped_column(String(20), default="", index=True)
    # pending | extracting | processing | ready | failed | need_transcript | committed
    status = mapped_column(String(50), index=True, default="pending")
    stage = mapped_column(String(80), default="")     # 当前阶段文案
    progress = mapped_column(Float, default=0.0)
    error_message = mapped_column(Text, default="")
    storage_path = mapped_column(String(1000), default="")  # 原件路径
    text_path = mapped_column(String(1000), default="")     # 抽取后的正文路径
```

**为什么这样设计**：
- **所有投递共用一张表**：电子书、笔记、网页、视频在"确认入库"前都只是"待解析的来源"，差异用 `type` 表达。下游队列 UI、重试、删除逻辑全部只需写一遍。
- **状态字段为什么是三个（status / stage / progress）而不是一个？** 三者分工不同：`status` 是粗粒度枚举，决定"能不能操作"（只有 ready 能入库）；`stage` 是细粒度文案（`extract_or_ocr`、`asr`），决定"界面上显示什么字"；`progress` 是 0-100 数字，驱动进度条。
- **为什么用状态机而不是布尔位？** 因为喂养是多步异步流水线（下载→抽文本→OCR/ASR→预览→入库），每步都可能失败或需要人工介入。枚举状态让每步的输入输出可校验、可恢复、可观测。

状态机的门禁（`service.py:610-618`）：

```python
    if row.status == "committed":
        raise HTTPException(status_code=409, detail="该来源已入库，请勿重复操作")
    if row.status != "ready":
        raise HTTPException(status_code=400, detail=f"仅 ready 状态可入库，当前为 {row.status}")
```

**作用**：保证流转方向只能是 `pending → extracting/processing → ready/need_transcript/failed → committed`。`committed` 是终态，防止重复入库产生重复知识条目。

### 第二步：投递端点——同步建行、异步解析

```python
# apps/api/app/modules/sources/router.py:66-79
@router.post("/upload", response_model=SourceOut, summary="上传电子书或笔记文件")
async def upload_source(
    background_tasks: BackgroundTasks,
    file: UploadFile = File(...),
    type: str = Form("ebook"),
    db: AsyncSession = Depends(get_db),
) -> SourceOut:
    row = await sources_service.create_upload(db, file=file, source_type=type)
    background_tasks.add_task(run_extract_job, row.id)
    return sources_service.to_out(row)
```

**为什么这样写**：
- `/paste`、`/url` 与 `/upload` 完全同构——**同步建行、同步落盘、异步解析、立即返回**。响应里带着 `pending` 状态的行 id，前端拿到后轮询。
- **为什么用 BackgroundTasks 而不是 Celery？** 单机个人工具，引入消息队列意味着多装一个 Redis、多管一个 worker 进程。BackgroundTasks 零依赖，响应返回后在同进程执行，够用。代价是进程重启会丢任务——但状态机兜底：重启后任务还是 `pending/processing`，用户点"重试"即可。

落盘的时序细节（`service.py:189-214`）：

```python
        row = Source(type=row_type, title=Path(filename).stem, status="pending", ...)
        db.add(row)
        await db.commit()
        await db.refresh(row)          # 拿到自增 id

        folder = _data_root() / "uploads" / str(row.id)
        folder.mkdir(parents=True, exist_ok=True)
        dest = folder / f"original{suffix}"   # 统一改名 original.ext
        dest.write_bytes(data)

        row.storage_path = str(dest.relative_to(_data_root())).replace("\\", "/")
        await db.commit()
```

**为什么两次 commit？** 需要自增 `row.id` 来命名目录 `uploads/{id}/`，所以必须先建行拿到 id，再写文件，再回写路径。**为什么统一改名 `original.ext`？** 用户文件名可能含中文、空格、甚至 `../` 路径注入——落盘名规范化，原始文件名只留在 DB 的 `filename` 字段里展示用。`.replace("\\", "/")` 是 Windows 兼容细节。

三种投递的"标志性文件"约定：
- 上传/粘贴 → `uploads/{id}/original.*`
- 链接 → `uploads/{id}/source.url`（若用户粘的是整段分享口令，原文还存一份 `share_raw.txt` 供排障）

**这个约定的价值**：后续解析器只认"目录里的标志文件"，与投递方式完全解耦。

### 第三步：后台任务——为什么不能复用请求的 Session

```python
# apps/api/app/modules/sources/tasks.py:13-25
async def run_extract_job(source_id: int) -> None:
    """必须每次动态取 SessionLocal，避免切库热切换后仍用旧引擎。"""
    try:
        factory = db_mod.SessionLocal
        if factory is None:
            db_mod.init_engine_from_config()
            factory = db_mod.SessionLocal
        async with factory() as db:
            await sources_service.process_extract(db, source_id)
    except Exception:
        logger.exception("extract job failed source_id=%s", source_id)
```

**两个关键设计**：
1. **只传 `source_id`，不传 `db` 对象**：请求作用域的 Session 在响应返回后就被依赖注入关闭了，后台任务里用它必然报错。任务内新建 Session，按 id 捞回数据行。
2. **每次动态取 `SessionLocal`**：注释点明了原因——设置页支持"数据库热切换"（功能点 14），如果模块加载时缓存了会话工厂，换库后后台任务还会写进旧库。这是"后台任务与连接生命周期"的经典坑。
3. **顶层 except 只记日志**：后台任务没有调用方接收异常。失败的对外信道是状态机——`process_extract` 最外层 catch 会把行置为 `failed` 并写入 `error_message`（前 500 字符），前端据此显示「重试」按钮。

### 第四步：失败分级——failed 与 need_transcript

```python
# service.py:904-911（终态失败）
        except Exception as exc:
            row.status = "failed"
            row.stage = "failed"
            row.error_message = str(exc)[:500]
            row.progress = 100
            await db.commit()
```

```python
# service.py:761-775（可恢复失败：ASR 没配好）
                except ValueError as asr_exc:
                    row.status = "need_transcript"
                    row.error_message = f"语音转写失败：{asr_exc}"[:500]
                    await db.commit()
                    return row
```

**为什么失败要分两级？** `failed` 是"机器彻底搞不定"（文件损坏等），用户只能重试或删除；`need_transcript` 是"机器缺条件"（无字幕视频且没配 ASR），转化为**等待人工**——用户通过 `POST /{id}/transcript` 补贴文案后直达 `ready`。**把"失败"变成"待办"，是这个状态机最妙的一笔。**

另一个细节：同步重活（yt-dlp / whisper / ffmpeg 都是阻塞 IO/CPU）用 `asyncio.to_thread` 丢线程池，避免卡死事件循环导致所有请求排队。

## 4. 完整流程图

```
用户投递
 ├─ 上传文件 ──▶ uploads/{id}/original.ext
 ├─ 粘贴笔记 ──▶ uploads/{id}/original.md
 └─ 贴链接 ────▶ uploads/{id}/source.url (+share_raw.txt)
        │  （建行 commit → 拿 id → 落盘 → 回写路径，status=pending）
        ▼
BackgroundTasks: run_extract_job(id)
        │  新建 Session → process_extract
        ▼
按 type 分派解析（功能点 04/05），每步 commit 上报 stage/progress
        ▼
统一产物 uploads/{id}/extracted.txt + status=ready
        ▼
用户预览确认 → POST /ingest（功能点 06）→ status=committed

异常路径：任何异常 → failed（可 /retry）；ASR 缺条件 → need_transcript（可 /transcript 补贴）
```

## 5. 关键文件与配置对照

| 文件 | 职责 |
|------|------|
| `apps/api/app/modules/sources/router.py` | 投递/队列/预览/入库/重试等全部端点 |
| `apps/api/app/modules/sources/service.py` | 建行落盘、`process_extract` 流水线、状态门禁 |

| 主要端点 | 说明 |
|----------|------|
| `POST /api/sources/upload` | 上传文件（ebook/note/video_file） |
| `POST /api/sources/paste` | 粘贴笔记正文 |
| `POST /api/sources/url` | 视频或网页链接（含分享口令解析） |
| `GET /api/sources` | 队列列表（前端轮询） |
| `GET /api/sources/{id}/preview` | 分段读 extracted.txt |
| `POST /api/sources/{id}/transcript` | 补贴文案（need_transcript → ready） |
| `POST /api/sources/{id}/retry` | 失败重试（重置回 pending） |

无环境变量配置；数据落在 `data/uploads/{source_id}/`。
